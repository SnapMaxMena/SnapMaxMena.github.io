Stored procedures & scoped transactions
Transactions are never nested. Each BEGIN/COMMIT pair is an independent scoped transaction.
A transaction cannot span stored procedure boundaries. BEGIN must pair with COMMIT/ROLLBACK in the SAME procedure scope.
A transaction open at the end of a stored procedure → implicitly rolled back with an error.
DDL in inner SP while outer txn is active → Modifying a transaction that has started at a different scope is not allowed
Each transaction ID is a unique signed 64-bit integer.
Pattern: BEGIN before CALL, COMMIT after CALL, SP body has NO BEGIN/COMMIT.
SP statements follow enclosing txn rules: all commit or all roll back together.
Effectively: the SP's statements are inlined into the enclosing transaction.
Pattern: SP body has its own BEGIN/COMMIT. Called with no enclosing txn.
Zero, one, or more transactions can exist inside one SP.
Each txn in SP starts and ends inside the SP — no crossing the SP boundary.
Scoped txn = autonomous. An inner ROLLBACK does NOT affect an outer COMMIT and vice versa.
p1 calls p2; p2 has its own txn → that txn commits/rolls back independently of p1's txn.
Overlapping scoped txns on same table → deadlock risk. Use only when necessary.
Useful pattern: log_table SP commits independently even if outer txn rolls back.
Missing COMMIT in inner SP → inner SP implicitly rolls back → outer SP also fails → outer txn statements rolled back.
AUTOCOMMIT=FALSE + SP with DML but no BEGIN/COMMIT → txn opens implicitly inside SP, rolls back at SP end.
Fix: either start txn BEFORE calling SP, or put BEGIN/COMMIT INSIDE the SP — never split across boundary.
Multi-threading: threads sharing one connection share the same txn. COMMIT by one thread affects all. Use separate connections per thread.
Failed statements within a transaction — the trap
A failed DML rolls back only that statement's changes — the transaction stays open.
If you COMMIT after a failed statement, successful statements before and after the failure are committed.
Snowsight: halts at first error. SnowSQL -f: continues past errors. Behavior varies by client.
To make any error abort the whole txn: ALTER SESSION SET TRANSACTION_ABORT_ON_ERROR = TRUE
READ COMMITTED isolation — exam rules
Only isolation level in Snowflake. A statement sees only data committed before the statement began.
Two statements in the same txn can see different data if another txn commits between them.
A statement does see changes made by prior statements in the same txn, even if not yet committed.
Cross-session read consistency: set READ_CONSISTENCY_MODE = 'GLOBAL' (ACCOUNTADMIN only) for near-concurrent consistency.
