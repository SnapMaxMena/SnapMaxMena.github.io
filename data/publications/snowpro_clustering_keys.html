Clustering keys & clustered tables
SnowPro Core — quick-review card
What it is & when to use it
Definition
Columns or expressions designated to co-locate related data in the same micro-partitions. Enables micro-partition pruning.
Target table
Multi-TB tables where natural clustering has degraded due to DML or suboptimal insert order.
Works on
Tables and materialized views. ✗ Not supported on hybrid tables (hybrid tables always cluster by primary key).
Signs you need it
Queries getting slower over time · High clustering depth · Extensive DML on large table
Cluster when… — cost vs benefit
✓ Good candidate
Multi-TB table (many micro-partitions)
Queries filter/sort on same columns
Selective queries (small % of rows)
High query-to-DML ratio
Queries benefit from same key
✗ Poor candidate
Small tables
High-frequency DML (INSERT/UPDATE/DELETE)
Queries scan most/all of the table
Different queries use different columns
Hybrid tables (use PK instead)
⚠ Clustering is not for all tables. Credits are consumed for initial clustering AND ongoing automatic reclustering. Only cluster if query gains outweigh costs.
Cardinality — the key selection rule
✗ Too Low
IS_NEW_CUSTOMER (boolean) → minimal pruning
✓ Sweet spot
Date, region, event_type → effective pruning + grouping
⚠ Too High
Nanosecond timestamp, UUID → expensive, poor grouping
Fix high cardinality: use an expression to reduce distinct values, e.g. TO_DATE(c_timestamp) instead of raw timestamp · TRUNC(number, -5) to truncate digits.
How to pick the right key — priority order
Max 3-4 columns. More columns = more cost, less benefit.
① Columns used in selective WHERE filters (most important) — e.g. date column for "WHERE date BETWEEN x AND y"
② Columns used in JOIN predicates
③ GROUP BY / ORDER BY columns — helpful but less impactful than filters/joins
Multi-column order matters: put lowest cardinality first, highest cardinality last.
VARCHAR clustering key uses only the first 5 bytes. If all rows share the same prefix, cluster on a substring starting after the common prefix.
Reclustering — what happens
Trigger
DML (INSERT/UPDATE/DELETE/MERGE/COPY) degrades clustering over time
How it works
Snowflake deletes affected rows and re-inserts them grouped by clustering key → new micro-partitions created
Automatic?
✓ Yes — Automatic Clustering runs in background. No manual maintenance needed.
Cost
Consumes credits (compute) + storage (old micro-partitions retained for Time Travel + Fail-safe: min 8 days, up to 97 days)
Old micro-partitions are marked deleted but NOT immediately purged — retained for Time Travel & Fail-safe. This increases storage costs during reclustering.
SQL quick reference
CREATE with clustering key
CREATE TABLE t1 (c1 DATE, c2 STRING) CLUSTER BY (c1, c2);
ADD / CHANGE clustering key
ALTER TABLE t1 CLUSTER BY (c1, c3);
DROP clustering key
ALTER TABLE t1 DROP CLUSTERING KEY;
Check clustering info
SELECT SYSTEM$CLUSTERING_INFORMATION('t1');
-- or with specific columns:
SELECT SYSTEM$CLUSTERING_INFORMATION('t1', '(c1, c2)');
Key on expression (reduce cardinality)
CREATE TABLE t2 (ts TIMESTAMP) CLUSTER BY (TO_DATE(ts));
Key on VARIANT path
CREATE TABLE t3 (v VARIANT) CLUSTER BY (v:"Data":id::NUMBER);
Clustering key — supported vs not supported data types
✓ Supported
Base columns · Expressions on columns · Expressions on VARIANT paths · Any data type except those listed as unsupported
✗ NOT supported directly
GEOGRAPHY · VARIANT directly (use expression with path instead) · OBJECT · ARRAY · Hybrid tables (always clustered by PK)
Cloning a clustered table copies the clustering key, but Automatic Clustering is suspended on the clone — must be manually resumed.
