What a micro-partition is
Numbers you must memorize

Micro-partition size

  • 50 MB – 500 MB uncompressed
  • Always stored compressed (smaller on disk)
  • Auto-created — never defined by user

Clustering depth

  • Measures overlap between partitions
  • Lower = better clustered
  • Empty table = depth 0
  • Constant state = no overlap = optimal

Pruning — how queries get fast
Step 1: Snowflake checks metadata (min/max per column per partition) → skips partitions where filter value can't exist.
Step 2: Within remaining partitions, scans only the referenced columns (columnar scanning).
⚠ Subqueries in predicates do NOT trigger pruning.
Everything else that's tested

Metadata stored per partition

  • Min & max value per column
  • Number of distinct values
  • Other optimization properties

DML & dropped columns

  • DELETE / UPDATE / MERGE use metadata
  • DROP COLUMN = metadata-only op
  • Data stays in storage until partitions expire

Monitoring functions

  • SYSTEM$CLUSTERING_DEPTH('table') — depth only
  • SYSTEM$CLUSTERING_INFORMATION('table') — full details incl. depth
Exam traps
Trap 1 — user defines micro-partitions
False. Micro-partitions are automatic and transparent. Users never define, manage, or see them directly.
Trap 2 — higher clustering depth = better
False. Lower depth = better. Depth 1 = optimal (no overlap). High depth = lots of overlap = more scanning.
Trap 3 — subquery predicates prune partitions
False. Snowflake cannot prune based on a predicate with a subquery, even if it resolves to a constant.
Trap 4 — dropping a column rewrites partitions
False. DROP COLUMN is a metadata-only operation. Data physically stays in storage.
Trap 5 — partitions never overlap
False. Micro-partitions can overlap in value ranges — this is by design to prevent skew. Clustering reduces overlap.
Practice questions
Score:0 / 0
1. What is the uncompressed size range of a single micro-partition?
50–500 MB uncompressed is the fixed range. In practice they're smaller because Snowflake always stores data compressed. This number appears directly in exam questions.
2. A table's clustering depth increases significantly over time. What is the most likely cause?
DML degrades clustering over time as new data is inserted in non-ideal order, increasing micro-partition overlap. High clustering depth = table needs reclustering.
3. A query filters using WHERE id = (SELECT MAX(id) FROM ref_table). Will Snowflake prune micro-partitions?
Explicit rule: Snowflake does NOT prune micro-partitions based on predicates containing subqueries — even when the subquery resolves to a constant value. Use literal values in filters for pruning to work.
4. What metadata does Snowflake store for each micro-partition?
Snowflake stores: range of values (min/max) per column, number of distinct values, and additional optimization properties. This metadata powers partition pruning without scanning actual data.
5. A developer drops a column from a large table. What happens to the micro-partitions containing that column's data?
DROP COLUMN is a metadata-only operation. Micro-partitions are NOT rewritten. The physical data remains in storage. This is why dropped column data can still consume storage until partitions naturally expire through Time Travel and Fail-safe.
