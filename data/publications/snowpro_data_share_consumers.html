Required privileges — who does what
To import a share / create DB from share
ACCOUNTADMIN or role with
IMPORT SHARE global privilege
+ CREATE DATABASE global privilege
To grant IMPORTED PRIVILEGES on the DB
Role that owns the DB (has OWNERSHIP)
OR role with MANAGE GRANTS global privilege
Only the role that creates the database can access it by default. You must explicitly grant access to other roles.
Two paths to grant access — depends on provider setup
Path A — No DB roles (standard)
GRANT IMPORTED PRIVILEGES ON DATABASE snow_sales TO ROLE analyst;

Grants broad access to all shared objects.
Path B — Provider used DB roles
SHOW DATABASE ROLES IN DATABASE c1;
GRANT DATABASE ROLE c1.r1 TO ROLE analyst;

Finer-grained: each DB role controls subset of objects.
A single share can include both DB-role-associated and non-associated objects simultaneously.

SHOW SHARES — reading the output
kind = INBOUND
Someone shared this TO you. You are the consumer.
kind = OUTBOUND
You shared this to others. You are the provider.
database_name = empty
Share received but no DB created yet from it.
owner_account
Format: orgname.account_name — the provider's account.
When DESC SHARE shows object names prefixed with <DB> → no local database has been created yet from that share.
Streams on shared objects — special rules
You CAN create streams on shared secure views and tables to track DML changes.
Provider must enable change tracking on the view/table first. If you can't create the stream → contact the provider.
Stream can become stale if not consumed within the data retention period. Check with provider for retention period.
Check staleness: DESCRIBE STREAM stream_name → if STALE = TRUE → stream may be stale.
Reader accounts — exception rule
If consuming data via a reader account, the consumer does NOT need to perform any of these steps — the provider's administrator already completed them.
Reader accounts are created by the data provider to give non-Snowflake customers access to shared data.
