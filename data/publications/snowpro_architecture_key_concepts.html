3-layer architecture — know every layer
⚙️ Layer 3 — Cloud Services
Coordinates ALL activities. Runs on cloud instances managed by Snowflake.
Includes: Authentication & access control · Horizon Catalog · Metadata management · Query parsing & optimization · Infrastructure management · Regulatory compliance
Also: SNOWFLAKE database + Information Schema
Requires NO warehouse for metadata ops (SHOW commands, DDL planning)
↕ decoupled
🖥️ Layer 2 — Compute (Virtual Warehouses)
Each WH = independent MPP cluster. No shared compute between warehouses → no performance impact on each other.
Processes SQL statements + Snowpark code (Java, Python, Scala) + Apache Spark workloads.
Can be started/stopped/resized without affecting data or other warehouses.
↕ decoupled
💾 Layer 1 — Database Storage
Data stored in Snowflake's optimized, compressed, columnar format in cloud storage.
Automatically divided into micro-partitions.
Snowflake manages: organization · file size · structure · compression · metadata · statistics.
Supports: structured · semi-structured · unstructured data.
Key exam rule: Storage, Compute, and Cloud Services are fully decoupled. You can scale each independently.
3 table types in storage layer
⬛ Snowflake tables
Columnar, compressed, micro-partitioned. Snowflake manages storage. Ideal for data warehouses. Supports structured + semi-structured + FILE type.
🔷 Iceberg tables
Data + metadata in external cloud storage you manage (S3, GCS, Azure). Ideal for data lakes/lakehouses you can't move to Snowflake.
⚡ Hybrid tables
Index-based reads/writes. Low latency + high throughput. Row locking + unique/referential constraints. For Unistore OLTP workloads.
