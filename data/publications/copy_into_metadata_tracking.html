COPY INTO metadata tracking explanation

Why COPY INTO loads 0 rows on re-run: Snowflake stores metadata about every file it has loaded. When you run COPY INTO again on the same file, Snowflake sees it in the metadata, skips it silently, and returns success with 0 rows loaded. The command doesn't fail — it just does nothing.
How to fix it — 3 options
Option 1 — new file
Upload a new file (different name) to the stage. Metadata tracks by filename, so a new name = treated as new.
Option 2 — clear metadata
Run ALTER STAGE <name> REFRESH or purge the load history via COPY INTO … PURGE = TRUE to remove old metadata.
Option 3 — force load (FORCE = TRUE)
COPY INTO mytable FROM @mystage FORCE = TRUE; — ignores metadata and reloads. Warning: can cause duplicate rows.
Exam trap
Files are NOT deleted after COPY INTO
The distractor option said files are removed from S3 after loading — this is false. Files stay in the stage unless you set PURGE = TRUE. Snowflake only tracks metadata; it never auto-deletes source files.
Memory hook
COPY INTO = bouncer with a list. Once your name (filename) is on the list, you're not getting back in — unless you change your name, clear the list, or bribe the bouncer with FORCE = TRUE.
