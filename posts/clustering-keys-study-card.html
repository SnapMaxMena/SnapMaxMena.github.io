Clustering Keys and Clustered Tables — SnowPro Core study card

Clustering key = tells Snowflake which column(s) to use to co-locate related rows into the same micro-partitions → fewer partitions scanned → faster queries. Reclustering is automatic.
Use clustering only when ALL 3 are true

✅ Good candidate

  • Table is multi-TB (many micro-partitions)
  • Queries filter/sort on same columns
  • Table is read-heavy, DML-light
  • Query selectivity is high (reads small % of rows)

❌ Bad candidate

  • Small tables (Snowflake natural clustering is fine)
  • High DML frequency (expensive to maintain)
  • No consistent filter pattern across queries
  • Hybrid tables — always ordered by PK, no clustering key
Cardinality sweet spot — most tested concept
Too LOW
e.g. boolean
SWEET SPOT
e.g. date, city
Too HIGH
e.g. nanosec timestamp
Too low (boolean) → minimal pruning
Too high (nanosec timestamp) → expensive, poor grouping
Fix high cardinality: use expression to reduce it
e.g. TO_DATE(c_timestamp) instead of raw timestamp
Rules the exam loves

Column selection order

  • 1st Columns in selective filters (WHERE)
  • 2nd Columns in JOIN predicates
  • 3rd GROUP BY / ORDER BY (least priority)

Multi-column key rules

  • Max 3–4 columns recommended
  • Order matters: lowest → highest cardinality
  • VARCHAR: only first 5 bytes used
  • Cannot use: GEOGRAPHY, VARIANT, OBJECT, ARRAY directly

Commands

Define: CREATE TABLE t CLUSTER BY (col1, col2)

Change: ALTER TABLE t CLUSTER BY (col1, col3)

Drop: ALTER TABLE t DROP CLUSTERING KEY

Inspect: SYSTEM$CLUSTERING_INFORMATION('table_name')

Reclustering — costs & side effects
Automatic — Snowflake handles it, no manual action needed. Reclustering consumes credits (serverless compute) + increases storage temporarily (old micro-partitions kept for Time Travel + Fail-safe before purge = min 8 days, up to 97 days).
Exam traps
Trap 1 — clustering for all tables
False. Only worth it for very large tables (multi-TB) with consistent query patterns. Small tables need nothing.
Trap 2 — immediate effect
After defining a clustering key, rows are NOT immediately reclustered. Snowflake reclusters only when beneficial.
Trap 3 — CLONE copies clustering key
True — clone copies the key BUT Automatic Clustering is suspended on the clone. Must be resumed manually.
Trap 4 — CTAS doesn't keep clustering key
CREATE TABLE … AS SELECT does NOT copy the clustering key. Define it separately afterward.
Trap 5 — VARIANT can be in a clustering key
Only via an expression with path + type. Cannot cluster directly on a VARIANT column.
Trap 6 — Hybrid tables
Hybrid tables cannot have clustering keys — always ordered by primary key.
Practice questions
Score:0 / 0
1. A fact table has a TIMESTAMP column with millions of distinct nanosecond values. You want to cluster on it. What should you do?
High cardinality = expensive clustering, poor micro-partition grouping. Fix: reduce cardinality via an expression. TO_DATE() reduces nanosecond timestamps to days — far fewer distinct values, much better pruning.
2. You define a clustering key on a populated table. When do existing rows get reclustered?
Reclustering is fully automatic in Snowflake. Defining the key doesn't trigger immediate reclustering — Snowflake evaluates when it's beneficial and runs it as a background serverless operation.
3. You clone a clustered table. What happens to the clustering key?
CLONE copies the clustering key definition, but suspends Automatic Clustering on the clone. You must explicitly resume it with ALTER TABLE RESUME RECLUSTER if needed.
4. Which column ordering is correct for a multi-column clustering key?
Always lowest → highest cardinality. A high-cardinality column before a low-cardinality one reduces clustering effectiveness on the latter. E.g. CLUSTER BY (region, date) not (date, region) if date has higher cardinality.
5. Which of the following CANNOT be used directly as a clustering key column type?
VARIANT, OBJECT, ARRAY, and GEOGRAPHY cannot be used directly as clustering key types. However, you CAN use a VARIANT column in a key if you provide an expression with path + type cast, e.g. v:"Data":id::number.
